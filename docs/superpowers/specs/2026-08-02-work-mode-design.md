# 집중 모드 (Work Mode) — 설계

> 생기부 점검 허브를 **진단서에서 작업 도구로** 바꾼다.
> 수정 제안 · 바이트 예산 편집기 · 진행 워크리스트를 한 화면에 묶는다.

**작성일:** 2026-08-02 · **브랜치:** `feat/work-mode` · **기준 커밋:** `2b37315`

---

## 1. 왜 만드는가

현재 도구는 "여기가 문제다"에서 멈춘다. 교사의 실제 작업은 그 다음부터다.

```
지금:  업로드 → 이슈 45건 발견 → (도구 끝)
       → NEIS 창으로 이동 → 학생 찾기 → 문장 찾기 → 고치기 → 돌아오기
       → 다음 학생 … 35번 반복
```

픽스처 3종 45건을 분류한 결과:

| | 건수 | |
|---|---:|---|
| 기계적으로 고칠 수 있는 것 | 11건 (24%) | 과거형·특수기호·괄호영문·유의어 |
| 사람이 판단할 것 | 34건 (76%) | 외국어 표기·지칭어·내면심리·역량어 |

특히 `CAUTION_TERMS`에 **대체어 57쌍이 이미 데이터로 존재**하는데 화면 표시에만 쓰이고 치환에는 쓰이지 않는다.

목표는 **다시 타이핑하지 않게 하는 것**이다.

## 2. 범위

### 넣는 것

| | |
|---|---|
| ① 수정 제안 | 원문/수정안 대조, 체크박스 선택 적용, 고친 전문 복사 |
| ② 바이트 예산 편집기 | 문장별 바이트, "이 문장 빼면 N B" 미리보기 |
| ③ 워크리스트 | 학생별 완료 체크, 진행률, 키보드 이동 |
| ④ 수정본 xlsx | NEIS 업로드용. 원본 양식 보존 |

교과세특(`subject.html`) · 창체·행특(`career.html`) 양쪽에 적용한다.

### 빼는 것 (YAGNI)

- 규칙 커스터마이즈 UI — 별도 과제
- 오프라인 PWA — 별도 과제
- 인쇄 레이아웃 — 별도 과제
- 자동 수정 일괄 적용 — 안전하지 않음 (§6)

## 3. 아키텍처

기존 JS 7개는 **한 글자도 바꾸지 않는다.** 새 모듈만 추가한다.

```
추가
  assets/css/work.css        집중 모드 스타일
  assets/js/suggest.js       SGB.suggest    finding → 수정 제안
  assets/js/writeback.js     SGB.writeback  원본 워크북 + 수정 → 새 xlsx
  assets/js/worklist.js      SGB.worklist   진행 상태 (localStorage)
  assets/js/work-app.js      집중 모드 컨트롤러 + 파일 캡처

수정 (HTML만)
  subject.html               <script> 5줄 + 진입 버튼 1개
  career.html                동일
```

### 3.1 파일을 두 번 올리지 않게 하는 법

수정본 xlsx를 만들려면 **원본 워크북 바이트**가 필요하다. 별도 HTML 페이지로 넘기면
파일을 다시 올려야 하므로, 집중 모드는 **같은 페이지 위의 전체화면 오버레이**로 만든다.

`work-app.js`가 파일 input의 `change`를 **독립적으로 한 번 더 구독**해 자기 사본을 갖는다.
리스너는 여러 개 붙일 수 있으므로 기존 앱 코드를 수정할 필요가 없다.

> **스크립트 순서 제약 (중요)**
> `career-app.js`는 `change` 핸들러 끝에서 `fileInputEl.value = ''`로 input을 비운다.
> 그 뒤에 실행되면 `files`가 이미 비어 있다. 따라서 **`work-app.js`를 `career-app.js`보다
> 먼저 로드**해야 한다. 같은 요소의 리스너는 등록 순서대로 실행되므로 이걸로 충분하다
> (capture 플래그는 at-target 단계에선 순서에 영향을 주지 않아 도움이 안 된다).
> `subject-app.js`는 input을 비우지 않지만 일관성을 위해 같은 순서를 쓴다.

드래그&드롭도 `uploadZone`의 `drop`을 같은 방식으로 구독한다.

### 3.2 모듈 경계

| 모듈 | 하는 일 | 의존 |
|---|---|---|
| `suggest.js` | 텍스트 + findings → 제안 목록. **DOM 모름** | 없음 (순수 함수) |
| `writeback.js` | 워크북 + 수정 맵 → 새 워크북 바이트. **DOM 모름** | `XLSX`, `SGB.parse._internal` |
| `worklist.js` | 진행 상태 CRUD. **DOM 모름** | `SGB.core.saveState/loadState` |
| `work-app.js` | 오버레이 DOM · 이벤트 · 위 3개 조율 | 전부 |

앞의 셋은 순수 로직이라 Node로 단독 테스트한다. 기존 모듈과 같은 이중 런타임 패턴을 따른다.

창체는 학생당 텍스트가 하나라 **학생 = 작업 단위**다.

## 5. 제안 엔진 (`suggest.js`)

### 5.1 계약

```js
SGB.suggest.build(text, findings) → [{
  span:  [s, e],        // 원문 인덱스
  from:  '정리했고',
  to:    '정리하고',     // null 이면 '직접 고치세요'
  rule:  'R3과거시제',
  kind:  'safe' | 'pattern' | 'manual' | 'cut',
  on:    true           // 기본 체크 상태
}]

SGB.suggest.cuts(text) → [...]   // 문장 단위 삭제 후보 (kind:'cut', on:false)
SGB.suggest.apply(text, suggestions) → '수정된 텍스트'
```

`cut`은 바이트 줄이기용 문장 삭제다. 같은 배열에 담아 **적용 경로를 하나로** 유지한다 (§11.1).

`apply`는 뒤에서 앞으로 치환해 인덱스가 밀리지 않게 한다.
겹치는 span은 뒤엣것을 버린다 (`buildAnnotatedHtml`과 같은 규칙).

### 5.2 제안 종류별 출처

| kind | 대상 | 출처 | 기본 |
|---|---|---|:---:|
| `safe` | 유의어 (57쌍) | **finding의 `note`에서 추출** | ☑ |
| `safe` | 특수기호 `·`/`~` 등 | 규칙 기반 치환표 | ☑ |
| `safe` | 굽은 따옴표 `''""` | 곧은 따옴표로 | ☑ |
| `safe` | 괄호 영문 `반론(counterargument)` | 괄호 제거 | ☑ |
| `pattern` | 과거형 | 자체 패턴표 (§5.3) | ☑ |
| `manual` | 그 외 전부 | 없음 — 표시만 | — |

**유의어를 note에서 뽑는 이유.** `rules-subject.js`는 `CAUTION_TERMS`를 노출하지 않는다.
57쌍을 복사해두면 CORE-LOGIC.md가 지적한 "상수 복제" 문제를 하나 더 만든다.
finding의 note가 `기재 유의어 — 대체 표현: 「동영상 플랫폼」` 형식이므로
`「(.+?)」`로 뽑아 쓴다. **note 형식에 의존하므로 회귀 테스트로 고정한다** (§7).

### 5.3 과거형 패턴표

검증된 것만 넣는다. 표에 없으면 `manual`로 떨어뜨린다.

```
했고 → 하고      했으며 → 하며     했음 → 함       했다 → 함
하였다 → 함      하였고 → 하고     하였으며 → 하며  하였음 → 함
였음 → 임        었다 → 음         었으나 → 으나    았다 → 음
```

제안하지 않는 예: `이끌었던`(관형형) · `나왔을`(관형형) · `느꼈다고`(인용 내부)

> 근거: `했→하` 단순 치환은 `작성했음 → 작성하음`처럼 말을 부순다.
> 어미 단위 표가 유일하게 안전한 방법이다.

## 6. 안전장치

1. **자동 적용 없음.** 모든 제안은 체크박스이고, 결과 미리보기가 항상 보인다.
   기본 체크는 속도를 위한 것이지 검토 생략이 아니다 — 미리보기가 그 역할을 한다.
2. **원본 무손상.** 업로드한 파일은 절대 덮어쓰지 않는다. 항상 새 파일로 내려받는다.
3. **되돌리기.** 체크 해제 = 즉시 원문. 상태는 학생별로 보존된다.
4. **manual은 손대지 않는다.** 제안 없이 위치만 짚어준다.

## 7. 수정본 xlsx (`writeback.js`)

### 7.1 검증 완료

원본 워크북을 들고 **세특 셀만 교체**해 다시 쓰는 방식이 동작함을 확인했다.

```
헤더행 보존      OK
행 수 5 → 5      OK
나머지 셀 무변    OK
재파싱           standard / 학생 4명 / 과목 [국어, 수학]
```

열 위치는 기존 `SGB.parse._internal.findColumnIndices`를 재사용한다. 기존 JS 무수정.

### 7.2 대상과 제외

| 상황 | xlsx | 이유 |
|---|:---:|---|
| 교과 · 표준 그리드 · 단일 파일 | O | |
| 교과 · 표준 그리드 · 다중 파일 | O (zip) | 파일별로 추적. JSZip 이미 로드됨 |
| 교과 · **인쇄덤프** | **X** | NEIS 출력 보고서라 되올릴 양식이 아님 |
| 창체 · 단일 파일 | O | |
| 창체 · **다중 파일** | **X** | 학생당 텍스트로 병합돼 출처 파일 추적 불가 |

제외 상황에서는 버튼을 숨기고 **이유를 화면에 적는다.** 조용히 실패하지 않는다.

### 7.3 창체 번들 양식

`parseCareerBundleRows`는 `career-app.js`에 있고 노출되지 않는다.
헤더 탐색(번호+성명+특기사항) + 본문 4번째 열 고정이라 로직이 짧으므로
`writeback.js`에 다시 구현한다. **같은 셀을 찾는지 테스트로 대조**한다.

## 8. 진행 상태 (`worklist.js`)

```js
// localStorage: sgb_worklist_v1
{
  "3/1|김서연|국어": { done: true,  edits: { "12": false } },
  "3/1|김서연|수학": { done: false, edits: {} }
}
```

- **키** = `번호|성명|과목` (창체는 `번호|성명|활동유형`). 기존 병합 키와 같은 규칙이라
  파일을 다시 올려도 진행 상태가 붙는다.
- `edits`는 **기본값에서 벗어난 것만** 저장한다. 기본 체크가 대부분이므로 저장량이 작다.
- 기존 `sgb_subject_v1` / `sgb_career_v1` 스키마는 건드리지 않는다. 별도 키를 쓴다.

## 9. 테스트

### 9.1 속성 테스트 (핵심)

> **제안을 적용한 뒤 다시 스캔하면, 그 finding이 사라져야 한다.**

```js
const before = RS.scan(text, profile);
const after  = RS.scan(SGB.suggest.apply(text, sugg), profile);
// sugg 가 겨냥한 rule 은 after 에서 사라졌는가?
// after 에 before 에 없던 새 finding 이 생기지 않았는가?
```

틀린 제안은 여기서 자동으로 걸린다. 픽스처 전체에 대해 돌린다.

### 9.2 나머지

| 대상 | 확인 |
|---|---|
| 패턴표 | 12개 항목 전수 from→to |
| note 파싱 | `「」` 추출이 실제 finding에서 동작 (형식 회귀 감시) |
| `apply` | 겹치는 span, 역순 치환으로 인덱스 안 밀림, 빈 제안 |
| writeback | 구조 보존, 다중 파일 zip, 인쇄덤프 거부 |
| 창체 번들 | 재구현한 셀 탐색이 `career-app.js` 결과와 일치 |
| worklist | 저장·복원, 재업로드 후 상태 유지 |
| E2E | 업로드 → 집중 모드 → 수정 → 내려받기 → **재업로드 시 이슈 감소 확인** |

마지막 E2E가 진짜 증명이다. 고친 파일을 다시 올려 이슈가 줄면 도구가 실제로 작동한 것이다.

각 단계가 독립적으로 동작하고 검증 가능하도록 쪼갠다.

1~3은 UI 없이 Node로 끝난다. 화면을 만들기 전에 로직이 옳은지 먼저 증명한다.

## 11. 결정 사항

### 11.1 문장 삭제와 수정 제안을 한 경로로 합친다

둘 다 텍스트를 바꾸므로 적용 순서가 결과를 좌우한다. 경로가 둘이면 순서 버그가 난다.
**문장 삭제를 `suggest` 목록의 한 항목으로 만든다.**

```js
{ span: [120, 240], from: '두 번째 문장 전체', to: '', rule: 'CUT', kind: 'cut', on: false }
```

`apply`는 기존대로 뒤에서 앞으로 한 번만 돌면 된다. 오른쪽 바이트 패널의 `⌫`는
이 항목의 `on`을 토글하는 것뿐이고, 가운데 수정안 목록에도 같이 나타난다.
문장 삭제는 되돌리기 어려운 조작이라 **기본값은 해제(`on: false`)**다.

### 11.2 수정본 파일명

| 상황 | 파일명 |
|---|---|
| 단일 파일 | `{원본파일명}_수정본.xlsx` |
| 다중 파일 (교과) | `saenggibu_수정본.zip` 안에 `{원본파일명}_수정본.xlsx` |

기존 `exportAllSubjectsZip`은 `saenggibu_과목별점검_전체.zip` 안에
`{과목}_점검결과.xlsx`를 넣는다. 최상위 zip 이름도 내부 파일명 규칙도 겹치지 않는다.
"점검결과"(진단)와 "수정본"(NEIS 업로드용)이 이름으로 구분된다.
